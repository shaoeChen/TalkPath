# TalkPath 專案憲章

本憲章為最高規則，所有 coding agent 必須確實遵守，並在開發過程中動態調整相關文件。

## 1. 文件管理
1. 所有文件類型的資料一律建立於 `docs/` 資料夾（根目錄僅保留 `AGENTS.md`、`CLAUDE.md`、`README.md`）。
2. `AGENTS.md` 始終維持 200 行以內；描述性事務、系統結構等資訊一律以連結引用（例如結構放在 `docs/STRUCTURE.md`），不寫在 `AGENTS.md` 內。
3. `CLAUDE.md` 內容始終只有 `@AGENTS.md`。
4. 所有文件以正體中文書寫。

## 2. 核心文件與流轉規則
- `IDEAS.md`：較破碎的想法。
- `PLANS.md`：有完整想法但非目前工作項目。
- `PROGRESS.md`：僅記錄當前執行中、未完成的工作，作為中斷後的交接資訊。來源若是實作計畫書，記錄該計畫書路徑；來源若是 `PLANS` 且未展開實作計畫，來源記錄為 `PLANS`。
- `HISTORY.md`：已完成的工作記錄。
- `INSIGHT.md`：討論過程中的關鍵洞察。
- `TECHSTACKS.md`：所採用的技術棧。
- `CONSTITUTION.md`：本憲章。

流轉規則（同一項目同一時間只存在於一處，不重複保留）：
1. 想法整理完整寫入 `PLANS` 後，同步從 `IDEAS` 刪除。
2. `PLANS` 項目展開實作計畫後，從 `PLANS` 刪除。
3. 簡單、不需展開實作計畫的項目，於工作完成後直接從 `PLANS` 刪除。
4. 工作完成後，進度寫入 `HISTORY` 並從 `PROGRESS` 刪除；因此 `PROGRESS` 永遠只有進行中的記錄，`HISTORY` 永遠只有已完成的記錄。

## 3. 開發原則
1. 遵守 MVP 最小開發原則：不過度開發，先完成最小可行性驗證。
2. 過程中思考出的延伸性開發，一律記錄於 `IDEAS.md`，作為下次討論依據，不得擅自實作。
3. 完成宣告前，必須執行與變更範圍相符的測試或檢查，並在 `PROGRESS`／`HISTORY` 記錄實際驗證結果；不得把骨架、介面或 fake provider 說成完整功能。

## 4. 澄清原則
開發過程中對有疑慮的部分（需求不明、多種做法、範圍不確定）必須向使用者提出澄清，不得由 coding agent 自行決定。

## 5. 動態維護
coding agent 須在過程中即時更新相關文件（想法、計畫、進度、歷史、洞察、技術棧、結構）。憲章本身的修改須經使用者同意。
